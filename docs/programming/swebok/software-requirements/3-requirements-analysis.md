# 3. Requirements Analysis

## Glossary

| Term | Definition | 中文翻译 | Source |
|---|---|---|---|
| **Requirements Analysis**<br>需求分析 | "Requirements analysis helps software developers **understand the meaning and implications of candidate requirements**, both **individually and in the context of the overall set of requirements**." | 需求分析帮助软件开发者**理解候选需求的含义和影响**，既**单独地看，也放在整套需求的背景下看**。 | [Washizaki, 2026, Chapter 1, section 3, para. 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Basic Requirements Analysis**<br>基本需求分析 | "The following list of **desirable properties of requirements** can **guide basic requirements analysis**." | 下面这份**需求的理想属性**清单可以**指导基本需求分析**。 | [Washizaki, 2026, Chapter 1, section 3.1, para. 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Unambiguous**<br>无歧义 | "be **unambiguous** (**interpretable in only one way**);" | **无歧义**（**只能有一种解读**）； | [Washizaki, 2026, Chapter 1, section 3.1, para. 1, item 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Testable**<br>可测试 | "be **testable** (quantified), meaning that **compliance or noncompliance can be clearly demonstrated**;" | **可测试**（已量化），即**符合与否能被清楚地证明**； | [Washizaki, 2026, Chapter 1, section 3.1, para. 1, item 2, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Binding**<br>有约束力 | "be **binding**, meaning that **clients are willing to pay for it** and unwilling not to have it;" | **有约束力**，即**委托方愿意为它付钱**，也不愿意没有它； | [Washizaki, 2026, Chapter 1, section 3.1, para. 1, item 3, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Atomic**<br>原子性 | "**atomic**, **represent a single decision**" | **原子性**，**只代表一个决定** | [Washizaki, 2026, Chapter 1, section 3.1, para. 1, item 4, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Complete**<br>完整 | "**complete** — The requirements **adequately address boundary conditions, exception conditions and security needs**;" | **完整**：这些需求**充分覆盖了边界条件、异常条件和安全需要**； | [Washizaki, 2026, Chapter 1, section 3.1, para. 2, item 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Concise**<br>简洁 | "**concise** — **No extraneous content** in the requirements" | **简洁**：需求中**没有多余内容** | [Washizaki, 2026, Chapter 1, section 3.1, para. 2, item 2, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Internally Consistent**<br>内部一致 | "**internally consistent** — **No requirement conflicts with any other**;" | **内部一致**：**没有任何一条需求与其他需求冲突**； | [Washizaki, 2026, Chapter 1, section 3.1, para. 2, item 3, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Externally Consistent**<br>外部一致 | "**externally consistent** — **No requirement conflicts with any source material**;" | **外部一致**：**没有任何一条需求与来源材料冲突**； | [Washizaki, 2026, Chapter 1, section 3.1, para. 2, item 4, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Feasible**<br>可行 | "**feasible** — A viable, cost-effective solution can be created **within cost, schedule, staffing, and other constraints**." | **可行**：能够**在成本、进度、人员和其他约束之内**做出一个可行且划算的方案。 | [Washizaki, 2026, Chapter 1, section 3.1, para. 2, item 5, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **5-Whys Technique**<br>五个为什么 | "The **5-whys technique** (e.g., [3*, c4]) involves **repeatedly asking, “Why is this the requirement?”** to **converge on the true problem**." | **五个为什么**（例如 [3*, c4]）指**反复追问「为什么这是需求？」**，以便**收敛到真正的问题**。 | [Washizaki, 2026, Chapter 1, section 3.1, para. 3, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Economics of Quality of Service Constraints**<br>服务质量约束的经济性 | "Quality of service constraints can be **particularly challenging**. This is generally because engineers **do not consider them from an economic perspective** [9, c4]." | 服务质量约束可能**特别棘手**，通常是因为工程师**没有从经济角度考虑它们** [9, c4]。 | [Washizaki, 2026, Chapter 1, section 3.2, para. 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Perfection Point**<br>完美点 | "**Perfection point** — This is the **most favorable level of performance**, beyond which **there is no additional benefit**." | **完美点**：**最理想的性能水平**，超过它就**不再有额外收益**。 | [Washizaki, 2026, Chapter 1, section 3.2, para. 3, item 1, p. 1-9](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Fail Point**<br>失败点 | "**Fail point** — This is the **least favorable level of performance**, beyond which **there is no further reduction in benefit**." | **失败点**：**最不理想的性能水平**，超过它收益**不再进一步下降**。 | [Washizaki, 2026, Chapter 1, section 3.2, para. 3, item 2, p. 1-9](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Most Cost-Effective Performance Level**<br>最具成本效益的性能水平 | "Figure 1.5 illustrates the **most cost-effective performance level** — the performance level with the **maximum positive difference between the value at that performance level and the cost to achieve it**." | 图 1.5 展示了**最具成本效益的性能水平**，即**该水平的价值与达到它的成本之间正差最大**的性能水平。 | [Washizaki, 2026, Chapter 1, section 3.2, para. 5, p. 1-9](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Formal Analysis**<br>形式化分析 | "**Formal analysis** has shown **benefits in some application domains**, particularly **high-integrity systems** (e.g., [5, c6])." | **形式化分析**已在**某些应用领域显示出好处**，尤其是**高完整性系统**（例如 [5, c6]）。 | [Washizaki, 2026, Chapter 1, section 3.3, para. 1, p. 1-9](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Addressing Conflict in Requirements**<br>处理需求冲突 | "One particularly important aspect of requirements analysis is **identifying and managing such conflicts** (e.g., [6, c17])." | 需求分析中特别重要的一个方面是**识别和管理这类冲突**（例如 [6, c17]）。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 1, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Project Scope Management**<br>项目范围管理 | "A specific example is **project scope management** — namely, **balancing what’s desired in the stated software product requirements with what can be accomplished** given the project requirements of cost, schedule, staffing and other project-level constraints." | 一个具体例子是**项目范围管理**，即在成本、进度、人员和其他项目级约束这些项目需求下，**在已陈述的软件产品需求所期望的内容与能够完成的内容之间取得平衡**。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 2, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Product Family Development**<br>产品族开发 | "Another approach is to apply **product family development** (e.g., [20]). This involves **separating requirements into two categories**." | 另一种方法是采用**产品族开发**（例如 [20]），也就是**把需求分成两类**。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 3, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Invariant Requirements**<br>不变需求 | "The first category contains the **invariant requirements**. These are **requirements that all stakeholders agree on**." | 第一类是**不变需求**，即**所有干系人都同意的需求**。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 3, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Variant Requirements**<br>可变需求 | "The second category contains the **variant requirements**, where **conflict exists**." | 第二类是**可变需求**，即**存在冲突的需求**。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 3, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Design to Invariants**<br>面向不变量设计 | "The software can be designed using **design to invariants** to **accommodate the invariant requirements** and design for change to incorporate customization points to configure an instance of the system to best fit relevant stakeholders." | 软件可以用**面向不变量设计**来**容纳不变需求**，并用面向变化设计加入定制点，把系统实例配置得最适合相关干系人。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 3, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Design for Change**<br>面向变化设计 | "The software can be designed using design to invariants to accommodate the invariant requirements and **design for change** to **incorporate customization points** to configure an instance of the system to best fit relevant stakeholders." | 软件可以用面向不变量设计来容纳不变需求，并用**面向变化设计**来**加入定制点**，把系统实例配置得最适合相关干系人。 | [Washizaki, 2026, Chapter 1, section 3.4, para. 3, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
