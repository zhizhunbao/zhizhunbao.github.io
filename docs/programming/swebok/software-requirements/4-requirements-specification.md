# 4. Requirements Specification

## Glossary

| Term | Definition | 中文翻译 | Source |
|---|---|---|---|
| **Requirements Specification**<br>需求规格说明 | "Requirements specification concerns **recording the requirements** so they can be both **remembered and communicated**." | 需求规格说明关注**把需求记录下来**，使其既能**被记住，也能被传达**。 | [Washizaki, 2026, Chapter 1, section 4, para. 1, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Audience Analysis**<br>受众分析 | "The most basic recommendation for requirements documentation is to **base decisions** on an **audience analysis**." | 对需求文档最基本的建议是：**做决定**要以一次**受众分析**为依据。 | [Washizaki, 2026, Chapter 1, section 4, para. 6, p. 1-11](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Natural Language Requirements Specifications**<br>自然语言需求规格说明 | "**Natural language requirements specifications** express requirements in **common, ordinary language**." | **自然语言需求规格说明**用**普通的日常语言**表达需求。 | [Washizaki, 2026, Chapter 1, section 4.1, para. 1, p. 1-11](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Unstructured Natural Language Requirements Specification**<br>非结构化自然语言需求规格说明 | "A typical **unstructured natural language requirements specification** is a **collection of statements in natural language**, such as, “The system shall . . . .”" | 典型的**非结构化自然语言需求规格说明**是**一组自然语言陈述**，例如「系统应……」。 | [Washizaki, 2026, Chapter 1, section 4.1, para. 2, p. 1-11](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Business Rules**<br>业务规则 | "For example, **business rules** are statements that **define or constrain some aspect of the structure or the behavior of the business** to be automated." | 例如，**业务规则**是**定义或约束待自动化业务的结构或行为某一方面**的陈述。 | [Washizaki, 2026, Chapter 1, section 4.1, para. 2, p. 1-11](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Structured Natural Language Requirements Specification**<br>结构化自然语言需求规格说明 | "**Structured natural language requirements specifications** impose **constraints on how the requirements are expressed**; the goal is to **increase precision and conciseness**." | **结构化自然语言需求规格说明**对**需求的表达方式加以约束**，目标是**提高精确性和简洁性**。 | [Washizaki, 2026, Chapter 1, section 4.2, para. 1, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Actor-Action Format**<br>参与者-动作格式 | "The simplest example might be the **actor-action format**. The **actor** is the entity responsible for carrying out the action, and **action** is what needs to happen." | 最简单的例子可能是**参与者-动作格式**。**参与者**是负责执行动作的实体，**动作**是需要发生的事。 | [Washizaki, 2026, Chapter 1, section 4.2, para. 2, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Use Case Specification Template**<br>用例规格说明模板 | "Another example is a **use case specification template**, as shown in **Figure 1.6**." | 另一个例子是**用例规格说明模板**，如**图 1.6** 所示。 | [Washizaki, 2026, Chapter 1, section 4.2, para. 3, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **User Story Format**<br>用户故事格式 | "The **user story format**, “**As a &lt;role&gt; I want &lt;capability&gt; so that &lt;benefit&gt;**” as well as decision tables are other examples." | **用户故事格式**「**作为 &lt;角色&gt;，我想要 &lt;能力&gt;，以便 &lt;收益&gt;**」以及决策表是另外的例子。 | [Washizaki, 2026, Chapter 1, section 4.2, para. 4, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Decision Tables**<br>决策表 | "The user story format, “As a &lt;role&gt; I want &lt;capability&gt; so that &lt;benefit&gt;” as well as **decision tables** are **other examples**." | 用户故事格式「作为 &lt;角色&gt;，我想要 &lt;能力&gt;，以便 &lt;收益&gt;」以及**决策表**是**另外的例子**。 | [Washizaki, 2026, Chapter 1, section 4.2, para. 4, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Acceptance Criteria-Based Requirements Specification**<br>基于验收标准的需求规格说明 | "In acceptance-based criteria requirements specification, the requirements are **written using test case language**, which is **very precise**." | 在基于验收标准的需求规格说明中，需求**用测试用例语言写成**，而测试用例语言**非常精确**。 | [Washizaki, 2026, Chapter 1, section 4.3, para. 9, p. 1-13](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Test Driven Development (TDD)**<br>测试驱动开发（TDD） | "The main idea of **TDD** is that **test cases precede construction**." | **TDD** 的核心思想是**测试用例先于构造**。 | [Washizaki, 2026, Chapter 1, section 4.3, para. 2, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Acceptance Test Driven Development (ATDD)**<br>验收测试驱动开发（ATDD） | "**ATDD** [2*, s3.2.3, s8.2] is a part of the **larger test driven development (TDD) approach**." | **ATDD** [2*, s3.2.3, s8.2] 是**更大的测试驱动开发（TDD）方法**的一部分。 | [Washizaki, 2026, Chapter 1, section 4.3, para. 2, p. 1-12](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Behavior Driven Development (BDD)**<br>行为驱动开发（BDD） | "In **BDD**, the unit of functionality is described as a **user story**, in a form such as this: “As a &lt;role&gt; I want &lt;capability&gt; so that &lt;benefit&gt;.”" | 在 **BDD** 中，功能单元被描述为一个**用户故事**，形式如：「作为 &lt;角色&gt;，我想要 &lt;能力&gt;，以便 &lt;收益&gt;。」 | [Washizaki, 2026, Chapter 1, section 4.3, para. 5, p. 1-13](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Scenarios**<br>场景 | "This leads to the identification and specification of a set of “**scenarios**” in this form: “**Given &lt;some context&gt; [and &lt;possibly more context&gt;], when &lt;stimulus&gt; then &lt;outcome&gt;** [and &lt;possibly more outcomes&gt;].”" | 由此识别并规定一组如下形式的「**场景**」：「**假定 &lt;某种情境&gt;［以及 &lt;可能更多的情境&gt;］，当 &lt;刺激&gt; 时，则 &lt;结果&gt;**［以及 &lt;可能更多的结果&gt;］。」 | [Washizaki, 2026, Chapter 1, section 4.3, para. 5, p. 1-13](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Model-Based Requirements Specification**<br>基于模型的需求规格说明 | "Another approach to **avoiding the inherent ambiguity of natural languages** is to **use modeling languages** such as selected elements of the unified modeling language™ (UML) or systems modeling language™ (SysML)." | **避免自然语言固有歧义**的另一种方法是**使用建模语言**，例如统一建模语言™（UML）或系统建模语言™（SysML）中选定的元素。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 1, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Structural Models**<br>结构模型 | "**Structural models** for **specifying policies to be enforced**: These are logical class models as described in, for example, [9, c8]." | **结构模型**用于**规定要执行的规则**：它们是逻辑类模型，例如 [9, c8] 所述。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 1, item 1, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Behavioral Models**<br>行为模型 | "**Behavioral models** for **specifying processes to be carried out**: These models include use case modeling as described in [9, c7], interaction diagrams as described in [9, c9] and state modeling as described in [9, c10]." | **行为模型**用于**规定要完成的流程**：包括 [9, c7] 所述的用例建模、[9, c9] 所述的交互图和 [9, c10] 所述的状态建模。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 1, item 2, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Agile Modeling**<br>敏捷建模 | "Agile modeling (see, for example, [10]) is the **least formal**. Agile models can be **little more than rough sketches** whose goal is to communicate important information rather than demonstrate proper use of modeling notations." | 敏捷建模（例如见 [10]）**形式化程度最低**。敏捷模型可以**只是粗略的草图**，目的是传达重要信息，而不是展示建模符号的正确用法。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 2, item 1, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Semiformal Modeling**<br>半形式化建模 | "Semiformal modeling, for example [9, c6-12], provides a **definition of the modeling language semantics** ([9, Appendix L]), but that definition has **not been formally proved to be complete and consistent**." | 半形式化建模（例如 [9, c6-12]）提供了**建模语言语义的定义**（[9, Appendix L]），但该定义**没有被形式化地证明是完整且一致的**。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 2, item 2, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Formal Modeling**<br>形式化建模 | "Formal modeling, for example, Z, the Vienna development method (VDM), specification and description language (SDL) and [5, c7] have **very precisely defined semantics** that allow specifications to be **mechanically analyzed** for the presence or absence of specific properties to help avoid critical reasoning errors." | 形式化建模（例如 Z、维也纳开发方法（VDM）、规格与描述语言（SDL）以及 [5, c7]）具有**定义非常精确的语义**，使规格说明能被**机械地分析**是否具有特定属性，帮助避免关键的推理错误。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 2, item 3, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Correctness by Construction**<br>构造即正确 | "The term **correctness by construction** has been **used for development in this context**." | **构造即正确**一词**被用于这种语境下的开发**。 | [Washizaki, 2026, Chapter 1, section 4.4, para. 2, item 3, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Additional Attributes of Requirements**<br>需求的附加属性 | "Over and above the basic requirements statements already described, **documenting additional attributes** for some or all requirements **can be useful**." | 在已述的基本需求陈述之外，为部分或全部需求**记录附加属性**，**会有用**。 | [Washizaki, 2026, Chapter 1, section 4.5, para. 1, p. 1-14](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Planguage**<br>Planguage（规划语言） | "**Gilb’s Planguage** (short for Planning Language) [7] recommends attributes such as **scale, meter, minimum, target, outstanding, past, trend and record**." | **Gilb 的 Planguage**（Planning Language 的简称）[7] 推荐的属性有**标度、计量方法、最低值、目标值、杰出值、过去值、趋势和纪录**。 | [Washizaki, 2026, Chapter 1, section 4.5, para. 2, p. 1-15](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Incremental Specification**<br>增量式规格说明 | "In this approach, a version of the requirements specification **contains only the differences** — **additions, modifications and deletions** — from the previous version." | 在这种方法中，一个版本的需求规格说明**只包含与上一版的差异**，即**新增、修改和删除**。 | [Washizaki, 2026, Chapter 1, section 4.6, para. 1, p. 1-15](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Comprehensive Specification**<br>全面式规格说明 | "In this approach, each version’s requirements specification **contains all requirements**, **not just changes** from the previous version." | 在这种方法中，每个版本的需求规格说明**包含全部需求**，**不只是与上一版相比的变化**。 | [Washizaki, 2026, Chapter 1, section 4.6, para. 2, p. 1-15](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
