# Chapter 1: Software Requirements

## Glossary

| Term | Definition | 中文翻译 | Source |
|---|---|---|---|
| **Software Requirements**<br>软件需求 | "The Software Requirements KA concerns **developing software requirements** and **managing those requirements** over the software’s service life." | 软件需求知识领域关注**开发软件需求**，并在软件的整个服役期内**管理这些需求**。 | [Washizaki, 2026, Chapter 1, Introduction, para. 5, p. 1-2](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Requirements Engineering**<br>需求工程 | "The term **requirements engineering** is often used to denote the **systematic handling of requirements**." | **需求工程**一词常用来指**对需求的系统化处理**。 | [Washizaki, 2026, Chapter 1, Introduction, para. 6, p. 1-2](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Incompleteness**<br>不完整 | "incompleteness: **stakeholder requirements, and necessary detail, exist** that are **not revealed and communicated** to the software engineers" | 不完整：**存在某些干系人需求和必要细节**，却**没有被揭示并传达**给软件工程师 | [Washizaki, 2026, Chapter 1, Introduction, para. 3, item 1, p. 1-1](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Ambiguity**<br>歧义 | "ambiguity: requirements are communicated in a way that is **open to multiple interpretations**, with **only one possible interpretation being correct**." | 歧义：需求的表述方式**可以有多种解读**，而**只有一种解读是正确的**。 | [Washizaki, 2026, Chapter 1, Introduction, para. 3, item 2, p. 1-1](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **Defect**<br>缺陷 | "What is generally referred to as a bug — but is better called a **defect** — is simply an **observable difference between what the software is intended to do and what it does**." | 通常所说的 bug（更确切的叫法是**缺陷**）就是**软件本应做的事与它实际所做的事之间可观察到的差异**。 | [Washizaki, 2026, Chapter 1, Introduction, para. 4, p. 1-1](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[1. Software Requirements Fundamentals](1-software-requirements-fundamentals.md)**<br>软件需求基础 | (No definition) | （无定义） | [Washizaki, 2026, Chapter 1, section 1, p. 1-2](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[2. Requirements Elicitation](2-requirements-elicitation.md)**<br>需求获取 | "The goal of **requirements elicitation** is to **surface candidate requirements**." | **需求获取**的目标是**让候选需求浮现出来**。 | [Washizaki, 2026, Chapter 1, section 2, para. 1, p. 1-6](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[3. Requirements Analysis](3-requirements-analysis.md)**<br>需求分析 | "Requirements analysis helps software developers **understand the meaning and implications of candidate requirements**, both **individually and in the context of the overall set of requirements**." | 需求分析帮助软件开发者**理解候选需求的含义和影响**，既**单独地看，也放在整套需求的背景下看**。 | [Washizaki, 2026, Chapter 1, section 3, para. 1, p. 1-8](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[4. Requirements Specification](4-requirements-specification.md)**<br>需求规格说明 | "Requirements specification concerns **recording the requirements** so they can be both **remembered and communicated**." | 需求规格说明关注**把需求记录下来**，使其既能**被记住，也能被传达**。 | [Washizaki, 2026, Chapter 1, section 4, para. 1, p. 1-10](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[5. Requirements Validation](5-requirements-validation.md)**<br>需求确认 | "Requirements validation concerns **gaining confidence** that the requirements represent the **stakeholders’ true needs** as they are currently understood (and possibly documented)." | 需求确认关注**建立信心**，确信这些需求代表了按目前理解（并可能已记录）的**干系人的真实需要**。 | [Washizaki, 2026, Chapter 1, section 5, para. 1, p. 1-15](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[6. Requirements Management Activities](6-requirements-management-activities.md)**<br>需求管理活动 | "In contrast, **requirements management** can be thought of as “**maintaining that agreement over time**.”" | 相对地，**需求管理**可以看作「**随时间维护这一共识**」。 | [Washizaki, 2026, Chapter 1, section 6, para. 1, p. 1-16](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[7. Practical Considerations](7-practical-considerations.md)**<br>实践考量 | (No definition) | （无定义） | [Washizaki, 2026, Chapter 1, section 7, p. 1-17](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
| **[8. Software Requirements Tools](8-software-requirements-tools.md)**<br>软件需求工具 | "Tools that help software engineers deal with software requirements fall broadly into three categories: **requirements management tools**, **requirements modeling tools** and **functional test case generation tools**, as discussed below." | 帮助软件工程师处理软件需求的工具大致分为三类：**需求管理工具**、**需求建模工具**和**功能测试用例生成工具**，下文分别讨论。 | [Washizaki, 2026, Chapter 1, section 8, para. 1, p. 1-20](https://www.computer.org/education/bodies-of-knowledge/software-engineering/v4) |
